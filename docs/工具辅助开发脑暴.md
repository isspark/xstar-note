# XStar 笔记 · 工具辅助开发脑暴

> 本文记录 XStar 笔记后续可增加的工具与辅助能力，用于产品方向讨论、需求拆分和开发排期。
> 文中功能均为候选方案，不代表已经实现或已经确定进入下一版本。

---

## 1. 产品定位

XStar 笔记当前已经具备以下基础能力：

- 管理多个 Git 仓库，支持 Clone、Pull、Push、Commit 和冲突处理。
- 浏览、阅读和编辑 Markdown、代码及纯文本文件。
- 渲染 Markdown，支持任务清单、文档导航和相对路径图片。
- 预览 Mermaid 和 draw.io 图表。
- 管理独立于 Git 的本地 TODO，支持标签、分类、开始时间、截止时间和月历。
- 提供统一搜索、桌面小组件、任务通知、主题和动态取色等能力。

因此，后续产品不宜只增加普通的“笔记编辑”功能，更适合围绕下面三条主线发展：

1. 让知识库更容易被组织、检查和发现。
2. 让 Git 工作流更适合移动端使用。
3. 让笔记、TODO 和快速收集形成完整闭环。

推荐的产品主线是：

> **Git 知识库工作台：快速记录、结构化整理、任务追踪、移动端同步。**

## 3. 知识库辅助工具

### 3.1 双向链接与知识图谱

支持在 Markdown 中使用类似下面的链接：

```markdown
[[登录流程]]
[[项目规划]]
[登录流程](notes/login-flow.md)
```

候选能力：

- 显示当前文档引用的文档。
- 显示引用当前文档的反向链接。
- 扫描不存在目标文档的失效链接。
- 找出没有被任何文档引用的孤立文档。
- 提供简单的文档关系图。
- 点击关系节点直接打开文档。

建议分两步实施：

1. 第一版只实现链接解析、关联文档、失效链接和孤立文档扫描。
2. 第二版再增加仓库级关系图，避免一开始投入过多图形交互工作。

### 3.2 仓库知识库索引

为每个 Git 仓库生成知识库概览页，展示：

- Markdown 文档数量。
- 最近修改的文档。
- 按目录统计文档数量。
- 文档标题目录。
- 包含 TODO 的文档。
- 包含 Mermaid 或 draw.io 的文档。
- 未被引用的文档。
- 失效链接数量。
- 空文档和超长文档。
- 最近活跃目录。

示例：

```text
xstar-note
├── 42 篇 Markdown
├── 18 个待办项
├── 7 个 Mermaid 图
├── 3 个失效链接
├── 5 个孤立文档
└── 最近活跃：docs/
```

### 3.3 Markdown 文档诊断器

提供当前文件、当前目录和整个仓库三个检查范围，候选规则包括：

- 标题层级跳跃。
- 空标题或重复标题。
- 失效的相对链接。
- 图片文件不存在。
- 图片未被任何文档引用。
- TODO 格式异常。
- 代码块未闭合。
- Mermaid 代码块无法解析。
- 文档缺少一级标题。
- Front Matter 格式错误。
- 文件末尾缺少换行。

每条诊断结果应包含：

- 问题级别：错误、警告或提示。
- 文件路径。
- 行号。
- 问题说明。
- 建议操作。

点击问题后直接跳转到编辑器对应位置，可以把诊断器从静态报告变成真正的修复工具。

### 3.4 文档模板系统

模板可以保存到仓库中的 `.xstar/templates/` 目录，使模板本身也能通过 Git 同步。

建议内置模板：

- 日记。
- 会议纪要。
- 技术方案。
- 问题排查。
- 项目规划。
- 读书笔记。
- API 记录。
- 周报与复盘。

示例模板：

```markdown
# 问题标题

## 现象

## 环境

## 原因

## 解决方案

## 后续 action

- [ ]
```

### 3.5 Front Matter 管理器

支持 Markdown 文档顶部的元数据：

```yaml
---
title: 登录流程
status: draft
tags:
  - android
  - auth
created: 2026-09-08
---
```

候选能力：

- 自动生成 Front Matter。
- 编辑标题、状态、标签和日期。
- 按元数据筛选文档。
- 按状态统计文档。
- 生成文档索引。

该方向建议放在文档索引和诊断器之后，先明确元数据规范再实现批量能力。

## 4. 笔记与 TODO 闭环

### 4.1 从 Markdown TODO 转换为本地 TODO

对文档中的任务清单提供“转为本地 TODO”操作：

```markdown
- [ ] 完成登录流程设计
```

候选模式：

- 仅导入，不建立关联。
- 导入并建立关联。
- 本地 TODO 完成时同步修改 Markdown。

关联后可以在原文写入标识：

```markdown
- [x] 完成登录流程设计 <!-- xstar-todo:123 -->
```

需要重点处理：

- 文档被重命名或移动后的关联稳定性。
- 同一任务被多次导入时的去重。
- 文档和本地 TODO 同时修改时的冲突处理。
- 用户是否允许自动修改仓库文件。

### 4.2 TODO 关联文档

给本地 TODO 增加可选的文档来源：

```text
任务：补充同步冲突说明
来源：xstar-note/docs/同步冲突.md
```

可以关联：

- 仓库。
- 文件路径。
- 标题或锚点。
- 可选行号。

使用体验：

- 点击任务直接打开关联文档。
- 在文档页查看相关 TODO。
- 在工作台同时展示任务和来源文档。

建议增加独立关系表，而不是把仓库路径直接塞进 TODO 主表：

```text
todo_documents
- todoId
- repoId
- relPath
- anchor
```

### 4.3 TODO 整理助手

针对长期使用后的 TODO 数据提供整理页：

- 疑似重复项。
- 超过一段时间未更新的任务。
- 已过期任务。
- 无分类任务。
- 无时间任务。
- 已完成超过一段时间的任务。
- 标题为空或过短的任务。

批量操作：

- 合并。
- 删除。
- 设置分类。
- 设置截止时间。
- 批量归档。

### 4.4 周回顾与工作统计

基于现有 `createdAt`、`updatedAt`、`done`、`startAt` 和 `dueAt` 生成：

- 本周新增 TODO。
- 本周完成 TODO。
- 完成率。
- 逾期数量。
- 各分类完成数量。
- 各仓库文档修改数量。
- 最近最活跃仓库。
- 平均完成周期。

第一版不需要复杂图表，统计卡片、简单柱状图和趋势数字即可。

### 4.5 周期任务

支持每天、每周、每月、工作日和自定义间隔。

示例：

```text
每周一：整理本周计划
每月 1 日：检查备份
每天 18:00：记录工作总结
```

建议使用独立表：

```text
todo_recurring_rules
- id
- todoId
- rule
- nextTriggerAt
- enabled
```

不要把周期规则直接混入一次性 TODO 的字段中，避免后续状态语义复杂化。

## 5. Git 移动工作流工具

### 5.1 Git Diff 查看器

现有项目已经支持编辑、提交和同步，下一步可以补足“查看改了什么”的能力。

候选能力：

- 查看工作区未提交文件。
- 显示新增、修改、删除和重命名状态。
- 查看单文件 Diff。
- 行级新增和删除高亮。
- 只提交当前文件。
- 只提交选中的文件。
- 输入 Commit Message。
- 查看最近提交记录。

这是最值得优先开发的 Git 工具之一，因为它能直接降低移动端提交代码和文档的风险。

### 5.2 提交历史浏览器

仓库中增加历史入口：

- 最近提交列表。
- 提交时间、提交者和提交信息。
- 每次提交修改的文件列表。
- 查看提交 Diff。
- 查看某个文件的历史版本。
- 恢复单个文件到历史版本。
- 将历史内容复制为新文件。

第一版不建议直接做完整分支管理，优先聚焦查看历史、Diff 和单文件恢复。

### 5.3 冲突解决器增强

当前已有“保留本地”和“保留远程”的冲突处理，可以继续增加：

- 冲突文件内容预览。
- 冲突标记高亮。
- 本地版本和远程版本双栏展示。
- 手动编辑最终结果。
- 一键接受某一侧。
- 批量解决。
- 未解决冲突时阻止 Push。

建议先做双栏模式，不要一开始实现桌面 IDE 级别的完整三方合并。

### 5.4 同步诊断中心

将底层 Git 错误转换为用户可理解的诊断：

- 网络不可用。
- Token 失效。
- 没有 Push 权限。
- 远程分支不存在。
- 本地存在未提交修改。
- 存在冲突。
- 远程仓库已被删除。
- Git 历史不一致。
- 文件写入失败。

每个诊断应包含：

```text
问题原因
建议操作
重试按钮
复制错误详情
```

可以保存最近的同步记录，例如：

```text
09:31 Pull 成功
09:32 Commit 成功
09:33 Push 失败：Token 无效
```

### 5.5 离线同步队列

移动端网络不稳定时，建议支持：

- 编辑先保存本地。
- Commit 先执行本地操作。
- Push 失败后进入待同步队列。
- 网络恢复后提醒同步。
- 用户可以手动重试。
- 每个仓库显示待同步数量。

当前已有“本地已提交但未推送”的状态，可以继续演进为真正的同步队列。

### 5.6 仓库健康检查

为每个仓库提供检查报告：

- 是否存在未提交修改。
- 是否存在未推送提交。
- 当前分支。
- 远程地址。
- 最近同步时间。
- Token 是否可用。
- 是否存在冲突。
- 仓库大小。
- 大文件列表。
- 是否存在 `.gitignore`。
- 是否存在未被引用的图片资源。

该工具可以和 Markdown 文档诊断器合并为统一的“仓库检查”入口。

## 6. Markdown 与资源管理

### 6.1 图片和附件管理器

在已有图片预览基础上增加：

- 查看仓库全部图片。
- 按目录分组。
- 显示图片尺寸和文件大小。
- 找出未被 Markdown 引用的图片。
- 找出 Markdown 引用但文件不存在的图片。
- 批量压缩图片。
- 图片重命名和移动。
- 自动更新 Markdown 图片引用。
- 从系统分享图片到当前文档。

### 6.2 链接和资源重构

当文件被重命名或移动时，自动更新引用：

```markdown
![架构图](images/old-name.png)
```

改名后自动变为：

```markdown
![架构图](images/new-name.png)
```

建议把普通的“重命名文件”流程增强为：

1. 扫描仓库引用。
2. 显示将受影响的文件。
3. 用户确认。
4. 执行文件重命名。
5. 批量更新引用。
6. 生成一次 Commit。

### 6.3 文档批量操作

候选操作：

- 批量重命名。
- 批量移动目录。
- 批量加标签。
- 批量搜索替换。
- 批量修改标题。
- 批量转换编码。
- 批量导出 PDF 或 HTML。
- 批量生成目录。
- 批量添加 Front Matter。

建议优先实现批量搜索替换、批量更新链接、批量转换编码和批量生成目录。

## 7. Mermaid 与 draw.io 工具增强

### 7.1 Mermaid 编辑器

当前 Mermaid 主要是从 Markdown 中提取代码并预览，后续可以增加：

- Mermaid 代码编辑。
- 实时预览。
- 错误行提示。
- 主题切换。
- 导出 PNG、SVG 或 WebP。
- 复制 SVG。
- 将 Mermaid 图保存为独立文件。
- 从独立 `.mmd` 文件打开。

这样 Mermaid 可以从阅读能力升级为可使用的图表工具。

### 7.2 draw.io 轻量编辑入口

当前 draw.io 仅支持预览，可以考虑两条路线。

**路线 A：外部编辑**

- 调起浏览器或系统中的 draw.io 应用。
- 编辑后通过分享或导入覆盖原文件。

**路线 B：内置轻量编辑**

- 修改 XML。
- 修改页面名称。
- 删除页面。
- 复制页面。
- 导出图片。

不建议短期内实现完整的 draw.io 图形编辑器，格式和交互成本都很高。

### 7.3 图表资产导出

为 Mermaid 和 draw.io 提供统一的：

- PNG 导出。
- SVG 导出。
- WebP 导出。
- PDF 导出。
- 系统分享。
- 保存到仓库 `assets` 目录。

## 8. 移动端效率工具

### 8.1 快捷指令面板

类似命令面板，支持：

- 新建 TODO。
- 新建 Markdown。
- 搜索文档。
- 打开最近文件。
- 同步当前仓库。
- 查看未提交修改。
- 导入和导出 TODO。
- 打开设置。
- 扫描仓库问题。

同时支持外接键盘快捷键，更适合平板、Chromebook 和桌面环境。

### 8.2 系统分享接收

增加 Android Share Target，接收：

- 浏览器分享的网页标题和链接。
- 其他 App 分享的文本。
- 图片。
- 文件。
- 代码片段。

接收后可以选择：

- 保存到 Inbox。
- 添加为 TODO。
- 追加到今日笔记。
- 创建 Markdown 文档。
- 保存到指定仓库。

### 8.3 Inbox 快速收集箱

所有临时内容先进入统一收集箱：

```text
Inbox
├── 从浏览器分享的文本
├── 待处理链接
├── 截图
├── 快速记录
└── 尚未分类的 TODO
```

之后再整理为文档、TODO、仓库文件或归档内容。这样可以减少记录时立即选择仓库、目录和分类的负担。

### 8.4 每日笔记与快速记录

可以自动创建类似下面的文件：

```text
daily/2026-09-08.md
```

候选操作：

- 快速记录一句话。
- 快速记录一个 TODO。
- 快速粘贴剪贴板内容。
- 快速拍照并插入 Markdown 图片。
- 快速追加当前时间。
- 将 Inbox 内容整理到今日笔记。

### 8.5 小组件增强

在现有 TODO 小组件基础上增加：

- 今日任务小组件。
- 快速新建 TODO。
- 快速新建笔记。
- 最近文档小组件。
- 仓库同步状态小组件。
- Inbox 小组件。
- 指定分类 TODO 小组件。

### 8.6 Android App Shortcuts

提供系统级快捷入口：

- 新建 TODO。
- 新建笔记。
- 搜索。
- 打开默认仓库。
- 打开 Inbox。
- 同步仓库。

如果后续接入 Android 系统 AI 或自动化工具，还可以进一步暴露创建 TODO、记录笔记等 App Function。

## 9. 备份、安全和迁移

### 9.1 完整数据备份与恢复

除了 Git 仓库内容，本地还保存了 TODO、分类、设置、仓库配置和关联关系，因此需要统一备份：

```text
xstar-backup-2026-09-08.zip
├── database.json
├── settings.json
├── repo-metadata.json
└── todo-export.md
```

支持：

- 导出全部本地数据。
- 导入本地数据。
- 选择性恢复。
- 备份前预览。
- 覆盖前确认。
- 加密备份。

### 9.2 Token 和仓库安全检查

可以增加安全提示和扫描：

- Token 是否可能失效。
- 是否有敏感信息被写入文件。
- 是否存在 `.env`、`*.pem`、`*.key` 等高风险文件。
- 是否存在疑似密码或 Access Token。
- 是否存在大文件。
- 是否可能误提交本地配置。

扫描结果默认只在本地展示，不应上传到远程仓库。

### 9.3 数据迁移和导入向导

后续可支持：

- Markdown 文件夹。
- Obsidian Vault。
- Notion 导出的 Markdown。
- Todoist CSV。
- Trello CSV。
- 通用任务 Markdown。
- JSON 或 CSV TODO。

第一版建议只支持 Markdown 文件夹、标准 `- [ ]` 任务和 CSV TODO，先把导入预览、去重和错误提示做好。

## 10. 推荐开发路线

### 第一阶段：高价值、低风险

目标是直接增强当前架构，不大幅改变数据模型。

1. Git Diff 查看器。
2. 提交历史浏览器。
3. 仓库健康检查。
4. 同步诊断中心。
5. Markdown 文档诊断器。
6. 图片和链接失效检查。
7. 快速新建 Markdown 和 TODO。
8. Inbox 基础能力。

### 第二阶段：形成产品特色

目标是让项目从 Git 文件浏览器变成知识库工作台。

1. 双向链接。
2. 仓库知识库索引。
3. TODO 关联文档。
4. Markdown TODO 与本地 TODO 关联。
5. 文档模板。
6. 每日笔记。
7. 图片和链接自动重构。

### 第三阶段：效率和自动化

目标是提高持续使用频率和自动化程度。

1. 离线同步队列。
2. 冲突双栏合并。
3. 周回顾统计。
4. 周期任务。
5. Android 分享接收。
6. App Shortcuts。
7. Mermaid 编辑和导出。
8. 完整备份与恢复。
9. 更多小组件。

## 11. 推荐的首批 MVP

如果只选择一批最值得先做的功能，建议是：

### MVP 1：Git Diff 与提交历史

解决移动端用户最直接的痛点：不知道改了什么、无法安全提交、无法快速回看历史。

### MVP 2：Markdown 文档诊断

利用现有文件遍历和 Markdown 能力，提供失效链接、缺失图片、标题结构和 TODO 格式检查。

### MVP 3：Inbox 快速收集

把“记录”从复杂的仓库文件操作中解耦出来，支持稍后整理为笔记或 TODO。

这三个 MVP 之间互相独立，适合分批交付，也能覆盖 Git、知识库和移动端效率三条主线。

## 12. 核心用户闭环

推荐最终形成下面的使用流程：

```text
快速收集
   ↓
保存到 Inbox
   ↓
整理为 Markdown 或 TODO
   ↓
关联文档和任务
   ↓
执行 Git Commit
   ↓
Push 同步
   ↓
通过工作台、小组件和通知持续跟进
```

后续所有新工具都可以用这个闭环衡量：

- 是否减少了记录成本。
- 是否降低了整理成本。
- 是否让内容更容易被发现。
- 是否让 Git 同步更可靠。
- 是否让任务更容易完成和复盘。

## 13. 待决策问题

在进入具体开发前，建议逐项确认：

- Inbox 数据是否独立于 Git，还是默认落到某个仓库。
- TODO 与 Markdown 是否允许双向自动同步。
- 双向链接采用 `[[标题]]`、路径链接，还是两者都支持。
- Front Matter 是否定义统一字段规范。
- Git Diff 是否允许部分文件提交。
- 是否允许 App 自动修改用户的 Markdown 引用。
- 备份文件是否必须加密。
- 周回顾统计是否只统计本地 TODO，还是同时统计 Git 活动。
- 是否需要优先适配平板、桌面窗口和外接键盘。
